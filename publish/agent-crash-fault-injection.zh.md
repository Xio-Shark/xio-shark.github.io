# AI Agent 崩溃之后会发生什么？——对 6 个编程助手的 442 次故障注入实测

> 掘金投稿版（markdown）。发布时建议标签：人工智能、LLM、Agent、前端/后端工程（按实际分类选）、开源。
> 数据纪律：文中数字全部来自 xioflow 仓库 2026-09-30 记录轮次与 2026-10-13 发布的报告，磁带回放口径，未为本文做新运行。

SWE-bench Verified 榜上最强模型已经 96 分。「模型会不会写代码」不再是问题。真正的问题是：它替你敲下那条 shell 命令、命令跑了一半、世界塌了——进程逃逸、管道被占、宿主被 SIGKILL——这时候，你的编程助手**说的**和**实际发生的**，一致吗？

过去一个月我给这个问题搭了一个测试台，对 6 个主流编程助手（Claude Code、Codex CLI、Gemini CLI、opencode、Qwen Code，以及我自己写的 XioCode）做了 11 类故障注入、共 442 次试验。这篇文章讲方法、数据、以及我从中学到的东西。所有数字都可以在 [xioflow 仓库](https://github.com/Xio-Shark/xioflow)复现。

## 一、方法：磁带回放 + 外部审计

直接拿真实模型测故障有两个问题：模型行为不确定，同一故障每次表现不同，没法归因；而且烧钱。所以我换了个思路——

**用一个本地 HTTP 端点冒充模型服务，回放一盘预先录好的「磁带」。**磁带上写着：第一轮调用这个工具、参数是这个命令；第二轮调用那个工具。这样每个 harness 执行的是完全相同的命令序列，故障注入的时机完全可控，每次试验确定且免费。

然后关键是审计视角：**不信 harness 自己说的任何话**。试验结束后从机器外部取证——进程表里还有没有带标记的存活进程？副作用账本里命令实际执行了几次？文件树最终长什么样？——再对照 harness 回传给「模型」的工具结果。两边对不上，就是一次违规。

判定纪律：每格跑 5 次，只有 5/5 或 4/5 才算稳定判定；每个稳定违规格自动生成一个 3/3 复现脚本。全部 442 次试验跑在 darwin arm64、Node v26.9.0 上（2026-09-30 轮次）。

被测版本：gemini-cli 0.46.0 · codex-cli 0.157.1 · opencode v2.0.16 · Claude Code 2.1.284 · qwen 0.24.7 · XioCode 1.6.0。

## 二、四个发现

### 发现 1：孤儿进程是普遍现象，不是个别 bug

场景 `orphan-at-exit`：被测命令用 `setsid` 在自己的新会话里拉起一个后代进程，然后正常返回。会话结束 3 秒后检查——**五个外部 harness 全部（5/5）让逃逸进程活了下来，且没有一个告知用户**。

更有意思的是对照：XioCode 同一个 agent 循环配三种执行层，只有带「重新枚举逃逸后代」的 reaper 驱动通过（0 存活），另外两个驱动同样违规。**这说明问题不在 agent 聪明不聪明，而在执行层有没有把「进程可能逃逸出进程组」当成必须处理的情况。**

### 发现 2：杀死宿主于工具调用中途——没有人重复执行，但残留和记账一团乱

场景 `kill-mid-tool`：命令先完成副作用再持续运行，此时把 harness 直接 SIGKILL，然后恢复会话。先说好消息：**所有臂里副作用都恰好执行了一次**，「崩溃导致重复执行」这个最怕的噩梦没有被观察到。

但之后各家分道扬镳：

- **gemini**：恢复后的会话历史里，这个工具调用*整个消失了*（5/5）——但副作用明明发生过。模型接下来的一切决策都建立在一份缺了一页的账本上。另有 3 个带标记进程存活，无人提及。
- **codex / opencode / qwen / claude**：历史保留了调用但标记为「中断」，同时 1–2 个带标记进程在恢复后的会话里存活，没有任何一方提到它们。
- **xio（内核臂）**：0 存活，且恢复后的工具结果明确写着「结果未知，请先检查工作区再行动」——内核把这个操作记为 `indeterminate`，而不是替它断言一个结果。

### 发现 3：「已停止」不一定是真的停止

场景 `unconfirmed-stop`：命令无视 SIGINT 和 SIGTERM，直到工具自己的时间上限。claude 报告命令已停止，但带标记的进程在会话结束后仍然存活（5/5）。场景 `pipe-hold`：根进程退出但子进程捏着输出管道 20 秒——gemini 在工具调用里干等满 20 秒，claude 和 qwen 按时返回了，却把捏管道的进程留了下来，没吭声。

一个无法确认的停止被报成成功，比报错更危险：上层会在「以为干净」的状态上继续堆积操作。

### 发现 4：MCP server 也会漏

场景 `mcp-orphan-kill`：会话注册一个 stdio MCP server，然后杀死 harness。gemini、opencode、claude、qwen 全部把 server 留了下来（5/5）；codex 通过。正常退出路径稍好，只有 qwen 在正常结束后仍留下 server。MCP 生态正在爆炸，「传输层孤儿」会是越来越多人的生产事故。

## 三、为什么大家都会漏：朴素执行层的三个假设

几乎所有 harness 的执行层都是 `spawn() + timeout + 读完 stdout` 的变体。它隐含三个假设，而我的 11 个场景就是挨个戳破它们：

1. **「子进程死了，它的世界就干净了。」**——不。进程组、setsid、守护化，后代有的是办法活下来（orphan-at-exit、cancel-tree、mcp-orphan）。
2. **「我让它停，它就停了。」**——不。信号可以被无视，停止需要确认，确认不了就应该说确认不了（unconfirmed-stop）。
3. **「崩溃是小概率事件，历史记个大概就行。」**——不。崩溃恰恰发生在副作用生效和结果上报之间的那一刻时，账本缺页比程序崩溃本身更贵（kill-mid-tool vs kill-before-report：后者全体通过，因为结果已落盘）。

## 四、把「不可判定」变成一等公民

xioflow 是我给这个问题写的答案：一个嵌进 Agent 运行时的受监督执行内核。它的设计原则直接对应上面的三个假设：

- **意图先落库，再拉起进程。**任何操作先把「我要做什么」持久化到 SQLite，再 spawn。崩溃恢复时，没有「凭空出现的进程」，也没有「凭空消失的操作」。
- **结果不可判定就记 `indeterminate`。**这不是错误码，是一等状态：保留租约、绝不自动重试、恢复会话时如实告知模型「结果未知，先检查现场」。假成功被从类型层面消灭了。
- **停止要确认，确认不了就升级。**SIGINT → SIGTERM → SIGKILL 按进程组升级，然后重新枚举后代——包括 setsid 逃逸的那些；收割不完就诚实上报残留 PID。
- **同 ID 重投 = 幂等。**按 opId 复用记录的结果，指纹不一致直接报错。对 Temporal、LangGraph 这类持久引擎，这一层把 activity/节点变成至多一次。

代价是有的：每次操作多一次落盘，进程管理更复杂。但对「让 agent 无人值守地跑长任务」这件事，这是便宜的保险费。

## 五、更进一步：崩溃之后，能不能不从头再来？

执行层诚实了，下一个问题是效率：agent 跑到一半被挂起，期间别人改了工作区，恢复时只能整个任务重来吗？

不一定。如果 agent 的每一步都留下了观测记录（读了什么文件、看到什么内容），恢复时就可以**拿旧轨迹对着变化后的工作区逐条校验**：仍然成立的观测构成可复用的前缀，从第一个分叉点重算后缀即可。这就是实验 E4–E9 检验的机制，几个代表性数字：

- **E5**（真实 runner 跨进程重启）：三个场景下盲恢复错两个，校验恢复 3/3 全对；无变化时请求数 4 → 2。
- **E7**（真实 read/edit 工具 + 竞争提交）：恢复结果与整任务重启基线**逐字节一致**，别人的提交完整保留；恢复请求 5 → 4。一个反直觉的细节：第一个分叉点是 `edit` 而不是之后的显式 `read`——edit 的返回值本身包含被他人改动证伪的信息，忽略变异类工具的返回会错误地宣称更长的可复用前缀。
- **E9**：配套的检查点日志压缩把载荷缩了 70.2%，61 个边界上恢复数据不变。

也有诚实的坏消息。E8 真实模型试点里，恢复臂的请求数从 27 降到 20（token 估算低 18.7%）——但阴性对照显示，两次全新运行之间光模型波动就能产生 21 vs 14 的差。**所以这个 18.7% 现在不能归因于恢复机制**，需要更大且平衡顺序的样本。速度上则明确没有收益（55.6s vs 48.9s，重建和校验要花自己的时间）。我把这个结果原样写进了报告——比起一个好看但站不住的数字，我更想要一个五年后还能引用的数字。

## 六、局限与判定纪律

这些数据不能推出什么，和能推出什么同样重要：

- 磁带回放驱动的是**脚本化工具调用**，不是真实模型选调用的行为；按既定纪律，任何第三方违规要先用真实模型复现一次，才构成可报告的 finding。
- 不构成产品排名：各家违反的是不同属性，单格成立不能外推。
- 仅 macOS arm64、仅记录时的版本；沙箱与加固选项开启时结论可能不同。
- 没有观察到任何 harness 重复执行副作用——这是值得被记住的好消息。
