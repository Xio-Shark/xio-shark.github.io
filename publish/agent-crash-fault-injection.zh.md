# AI Agent 崩溃之后会发生什么？——对 6 个编程助手的 442 次故障注入实测

> 掘金投稿版（markdown）。发布时建议标签：人工智能、LLM、Agent、开源。
> 数据纪律：文中数字全部来自 xioflow 仓库 2026-09-30 记录轮次与 2026-10-13 发布的报告，磁带回放口径，未为本文做新运行。

SWE-bench Verified 榜首已到 96 分，「模型会不会写代码」不再是主要问题。更实际的问题是：agent 执行的命令跑到一半出了意外——进程逃逸、管道被占、宿主被 SIGKILL——此时编程助手报告的，与机器上实际发生的，一致吗？

过去一个月我为这个问题搭了一个测试台，对 6 个主流编程助手（Claude Code、Codex CLI、Gemini CLI、opencode、Qwen Code，以及我自己的 XioCode）做了 11 类故障注入、共 442 次试验。本文记录方法、数据与结论，所有数字可在 [xioflow 仓库](https://github.com/Xio-Shark/xioflow)复现。

## 一、方法：磁带回放 + 外部审计

直接用真实模型测故障有两个困难：模型行为不确定，同一故障每次表现不同，难以归因；成本也高。因此改用磁带法——**用本地 HTTP 端点冒充模型服务，回放预先录制的工具调用序列**。每个 harness 执行完全相同的命令，故障注入时机完全可控，每次试验确定且免费。

审计视角同样关键：**不以 harness 的自述为准**。试验结束后从机器外部取证——进程表里是否还有带标记的存活进程？副作用账本里命令执行了几次？文件树最终状态如何？——再对照 harness 回传给「模型」的工具结果。两者不一致，记为一次违规。

判定纪律：每格 5 次试验，4/5 以上才算稳定；每个稳定违规格自动生成 3/3 复现脚本。442 次试验运行于 darwin arm64、Node v26.9.0（2026-09-30 轮次）。

被测版本：gemini-cli 0.46.0 · codex-cli 0.157.1 · opencode v2.0.16 · Claude Code 2.1.284 · qwen 0.24.7 · XioCode 1.6.0。

## 二、四个发现

### 发现 1：孤儿进程是普遍现象

场景 `orphan-at-exit`：命令用 `setsid` 在新会话里拉起一个后代进程后正常返回。会话结束 3 秒后检查，**五个外部 harness 均未清理该逃逸进程（5/5），也未在输出中说明**。

对照更有说服力：XioCode 同一个 agent 循环配三种执行层，只有带「重新枚举逃逸后代」的 reaper 驱动通过（0 存活），另外两个驱动同样违规。**差异在执行层，不在 agent 循环**——取决于执行层是否把「进程可能逃逸出进程组」当作必须处理的情况。

### 发现 2：宿主死于工具调用中途——无重复执行，但残留与历史记录有缺口

场景 `kill-mid-tool`：命令先完成副作用再持续运行，此时将 harness SIGKILL，随后恢复会话。先说结论中积极的一面：**所有臂中副作用都恰好执行了一次**，未观察到任何重复执行。

差异在恢复之后：

- **gemini**：恢复后的会话历史中该调用缺失（5/5），但其副作用确实发生过；另有 3 个带标记进程存活，未被提及。
- **codex / opencode / qwen / claude**：历史保留了调用并标记中断，但 1–2 个带标记进程在恢复后的会话中存活，未被提及。
- **xio（内核臂）**：0 存活，且恢复后的工具结果明确提示「结果未知，请先检查工作区」——内核将该操作记为 `indeterminate`，不替它断言结果。

### 发现 3：报告的「已停止」未必等于已停止

场景 `unconfirmed-stop`：命令无视 SIGINT 和 SIGTERM 直到工具时间上限。claude 报告命令已停止，但带标记进程在会话结束后仍存活（5/5）。场景 `pipe-hold`：根进程退出但子进程持有输出管道 20 秒——gemini 在调用内等待满 20 秒；claude 和 qwen 按时返回，但留下了持有管道的进程，未在结果中说明。

无法确认的停止被报为成功，比直接报错更难处理：上层会在误认为干净的状态上继续操作。

### 发现 4：MCP server 同样可能残留

场景 `mcp-orphan-kill`：会话注册一个 stdio MCP server 后杀死 harness。gemini、opencode、claude、qwen 均未回收该 server（5/5）；codex 通过。正常退出路径较好，仅 qwen 在正常结束后仍残留。随着 MCP 使用增多，传输层进程的归属管理值得更多注意。

## 三、朴素执行层的三个假设

多数 harness 的执行层是 `spawn() + timeout + 读完 stdout` 的变体，隐含三个假设。11 个场景逐一检验了它们：

1. **「子进程退出后环境就是干净的。」**进程组、setsid、守护化都可能让后代存活（orphan-at-exit、cancel-tree、mcp-orphan）。
2. **「发出停止信号即已停止。」**信号可能被无视；停止需要确认，无法确认时应如实报告（unconfirmed-stop）。
3. **「崩溃很少见，记录可以近似。」**崩溃若恰好落在副作用生效与结果上报之间，缺失的记录比崩溃本身影响更大（kill-mid-tool 与 kill-before-report 的对照：后者全体通过，因为结果已落盘）。

## 四、把「不可判定」变成一等公民

xioflow 是我针对这些问题写的受监督执行内核，设计原则与上面三个假设一一对应：

- **意图先落库，再拉起进程。**操作先持久化到 SQLite 再 spawn，崩溃恢复时不存在来源不明的进程或丢失记录的操作。
- **结果无法确认时记为 `indeterminate`。**这是一等状态而非错误码：保留租约、不自动重试、恢复时如实告知「结果未知，先检查现场」，从状态定义上避免假成功。
- **停止需确认，无法确认则升级。**SIGINT → SIGTERM → SIGKILL 按进程组升级，随后重新枚举后代（含 setsid 逃逸）；无法完全收割时如实上报残留 PID。
- **同 ID 重投幂等。**按 opId 复用已记录结果，指纹不一致则报错；对 Temporal、LangGraph 这类持久引擎，这一层可把 activity/节点变为至多一次。

代价是每次操作多一次落盘、进程管理更复杂。对无人值守的长任务而言，这是合理的成本。

## 五、崩溃之后，能否不从头再来？

执行层诚实之后是效率问题：agent 挂起期间工作区被他人改动，恢复时只能整任务重来吗？不一定。若每一步都留有观测记录，恢复时可**拿旧轨迹对变化后的工作区逐条校验**：仍成立的观测构成可复用前缀，只从第一个分叉点重算后缀。E4–E9 检验了这一机制，代表性数字：

- **E5**（真实 runner 跨进程重启）：盲恢复 3 场景错 2 个，校验恢复 3/3 全对；无变化时请求数 4 → 2。
- **E7**（真实 read/edit 工具 + 竞争提交）：恢复结果与整任务重启基线**逐字节一致**，他人提交完整保留；恢复请求 5 → 4。一个值得注意的细节：第一个分叉点是 `edit` 而非之后的显式 `read`——edit 的返回值本身携带了被他人改动证伪的信息，忽略变异类工具的返回会错误地宣称更长的可复用前缀。
- **E9**：检查点日志压缩使载荷减少 70.2%，61 个边界上恢复数据不变。

也有需要说明的阴性结果。E8 真实模型试点中，恢复臂请求数从 27 降到 20（token 估算低 18.7%），但阴性对照显示两次全新运行之间仅模型波动就能产生 21 vs 14 的差。**因此 18.7% 暂不能归因于恢复机制**，需要更大且平衡顺序的样本；速度上也没有收益（55.6s vs 48.9s，重建与校验自身有开销）。我将该结果原样保留在报告中——可核验的数字比好看的数字更有长期价值。

## 六、局限与判定纪律

- 磁带回放驱动的是**脚本化工具调用**，不代表真实模型选调用的行为；按既定纪律，任何第三方违规需经真实模型复现一次，才构成可报告的 finding。
- 不构成产品排名：各家违反的是不同属性，单格结果不能外推。
- 仅 macOS arm64、仅记录时的版本；开启沙箱与加固选项时结论可能不同。
- 未观察到任何 harness 重复执行副作用。
